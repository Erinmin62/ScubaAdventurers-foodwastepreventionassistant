Implement a Waste-Aware Reordering feature in my existing ExpiryGuard AI application.

IMPORTANT:
Inspect the existing codebase, data model, inventory features, expiry calculations, and UI before making changes. Reuse the existing components and data. Do not rebuild the app or remove existing features.

GOAL:
Automatically recommend how much of each ingredient a café should reorder, considering expiry risk, expected demand, current stock, incoming deliveries, and supplier constraints. Every proposed order change must require human approval before execution.

FEATURE REQUIREMENTS:

1. INVENTORY AND DEMAND ANALYSIS
- Read current inventory, quantities, units, expiry dates, costs, and incoming delivery quantities and dates from the existing data.
- Check whether the project already has demand, usage-rate, supplier lead-time, and minimum-order-quantity fields.
- If required information is missing, add a minimal configuration or synthetic-data field without breaking existing records.
- Clearly distinguish real data from assumptions and simulated estimates.

2. WASTE-RISK CALCULATION
- Identify expired ingredients and ingredients at risk of expiring before they can be used.
- Estimate potential waste quantity and financial value.
- Use first-expiring-first-out stock allocation when estimating consumption.
- Avoid double-counting current stock and incoming deliveries.
- Explain why each ingredient is flagged.

3. WASTE-AWARE REORDER ENGINE
- Calculate expected demand until the next replenishment.
- Account for current usable stock, incoming deliveries, supplier lead time, safety stock, and minimum order quantities where available.
- Calculate the recommended additional order quantity using deterministic, testable calculations.
- Recommend reducing, delaying, or skipping a reorder when sufficient stock is available and delaying it is operationally feasible.
- Do not automatically delay a confirmed delivery without explicit approval.
- Explain the recommended quantity and the reason for every recommendation.
- Do not claim machine-learning predictions unless a predictive model is actually implemented and evaluated.

4. PROPOSED ORDER PLAN
Create a dashboard showing:
- Ingredient name and current stock.
- Expiry risk and estimated potential waste cost.
- Incoming delivery quantity and date.
- Expected demand and recommended order quantity.
- Original versus proposed order quantity.
- Estimated purchasing cost and potential waste reduction.
- Explanation and assumptions for each recommendation.

5. HUMAN APPROVAL
- Generate a proposed order plan with status PENDING_APPROVAL.
- Provide Approve, Edit, and Reject actions.
- Let the owner review and edit quantities before approving.
- Display the estimated impact and full proposed changes before confirmation.
- Do not modify purchase orders or inventory before approval.
- Validate the approved plan on the server before execution.
- Prevent duplicate execution if the same approval is submitted more than once.
- Record the approver, timestamp, approved quantities, and decision.
- Rejected plans must not execute.

6. EXECUTION AND ACTIVITY LOG
- After approval, execute the approved actions in the existing simulated environment.
- Update the relevant simulated purchase order or inventory records.
- Record before-and-after values, action status, timestamp, and outcome.
- Handle failures without incorrectly marking an action as successful.
- Make it clear that simulated orders are not real supplier orders.

7. AUTOMATION
- Provide a button to run the analysis immediately.
- If the existing architecture supports scheduled jobs, implement a daily inventory scan.
- A scheduled scan may generate recommendations automatically, but must not bypass human approval.
- Avoid unnecessary background services or additional infrastructure.

8. TESTING
Test at least these scenarios:
- Enough stock and incoming deliveries: recommend no additional order.
- Insufficient stock: recommend an appropriate order quantity.
- Existing stock at risk of expiring: recommend a waste-prevention action.
- Incoming delivery arrives before additional stock is needed.
- Missing demand or supplier data: show an explicit assumption or request configuration.
- Owner edits and approves a proposal.
- Owner rejects a proposal.
- Failed execution and duplicate approval attempts.
